## Sample website launch plan (0b9081c)

Visitors without an .mpp file can now click "Try a sample plan →" in the
hero to instantly load a realistic 57-task website launch plan — no upload,
no import service round-trip.

### Design decisions

- **Personal ephemeral copy**: each click creates a fresh guest copy (24h
  TTL) via `/api/plansight/sample`. Concurrent users don't share state.
- **Date-shifting anchor**: the canonical plan has fixed base dates
  (2024-01-01). The route shifts every task start/finish so the project
  began 28 days before today, placing "today" at day 28. At that point
  the plan is mid-flight: 5 late tasks, 2 at-risk tasks, a blocked
  design-freeze milestone — a rich AI analysis target.
- **`owner_type = 'sample'`**: the canonical row is never touched by the
  guest-TTL cleanup query (which filters `.eq("owner_type", "guest")`).
- **`?sample=<shareId>` URL param**: distinct from `?shareId=` (which
  requires ownership). The page loads the sample via `loadSharedPlan`
  (anon read, no ownership check) and passes `isSample={true}` to the
  shell. Falls through silently if the 24h guest copy has expired.

### Files shipped

- `supabase/migrations/16_sample_website_launch_plan.sql` — canonical
  57-task plan. 7 phases: Kickoff, Discovery, Design, Development, Content,
  Testing & QA, Launch. Resources: PM, BA, Dev Lead, UX Designer, Creative
  Dir, Frontend Dev, Backend Dev, DevOps, Content, QA, SEO. Base dates

- `lib/plansight-ai/sample.ts` — pure `shiftSampleToCurrentDates(plan)`

- `app/api/plansight/sample/route.ts` — POST. Reads canonical sample via

- `components/plansight-ai/PlanSightHeroCta.tsx` — "Try a sample plan →"

- `app/products/plansight-ai/page.tsx` — handles `?sample=` param alongside

## Bug fix: sample plan loading (2eec939)

Two bugs surfaced immediately after the first deploy. The button got stuck
at "Preparing sample…" and the plan never loaded in the workspace.

### Root cause 1 — shell state not updating after soft navigation

`useState(initialPlan)` only reads `initialPlan` on first mount. After
`router.push('?sample=X')`, Next.js re-renders the Server Component with
the new `initialPlan`, but `PlanSightProductShell` stays mounted at the
same tree position — its `plan` state stays `null` and the workspace
never shows.

Fix: add `key={initialShareId ?? "empty"}` to `<PlanSightProductShell />`
in `page.tsx`. The shell remounts when the URL carries a new plan, so
`useState(initialPlan)` initialises correctly from the new prop. This also
benefits the existing `?shareId=` deep-link path.

### Root cause 2 — hero button never resets

`sampleLoading` was set to `true` before `router.push` and never reset.
Since the component stays mounted after soft navigation (same tree
position), the button stayed at "Preparing sample…" indefinitely.

Fix: call `setSampleLoading(false)` immediately after `router.push`.
The navigation is already in flight; resetting the button right away is
correct — the workspace handles the rest.

## Hero and header behaviour by auth state (433b82f, 0ecbfde, ebc0bb1, bf34111)

Four incremental passes to reach the right UX for each auth state on the
product page.

### Final behaviour matrix

| State | Above workspace |
|---|---|
| Anonymous, no plan | Full marketing hero (tagline, screenshot, upload CTA, sample CTA, See pricing) |
| Anonymous, sample loaded (`?sample=X`) | Nothing — straight to workspace |
| Signed in, no plan | Account header (same as `/my-plans`) |
| Signed in, plan pre-loaded (`?shareId=X` or `?sample=X`) | Account header (same as `/my-plans`) |

### Reasoning per decision

- **`433b82f` Hide hero when plan is pre-loaded**: when a user arrives
  via `?shareId=` or `?sample=`, they're in workspace mode — the marketing
  pitch is noise. Condition: `!initialPlan`.
- **`0ecbfde` Hide hero for signed-in users**: signed-in users already
  converted. The workspace upload form is their landing surface. Condition:
  `!initialPlan && !user`.
- **`ebc0bb1` Show My Plans header for signed-in users**: instead of
  showing nothing above the workspace for signed-in users, show the
  identical navy header from `/my-plans` — tier badge, h1, WeekStartDayToggle,
  Manage billing (Pro), descriptive paragraph, cancel-pending banner.
  Requires fetching `billing` for Pro users on the product page (same
  `getUserBilling` call as `/my-plans`).
- **`bf34111` Fix: header always shows for signed-in users**: the initial
  condition `user && !initialPlan` hid the header when a plan was
  pre-loaded via deep-link. Changed to `!!user` so the header always
  shows for signed-in users regardless of plan state.

### Data fetched for the account header

The product page now fetches `billing` (Pro users only) and computes
`cancelPending` / `cancelDate`, same as `/my-plans`. The `preferences`
fetch was already in place for the shell's `weekStartDay` prop and now
also feeds `WeekStartDayToggle` in the header.
