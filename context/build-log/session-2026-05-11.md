## Phase 5b — cancel-at-period-end UX banner

User reported that clicking Cancel in the Customer Portal kept them
showing as Pro afterward. Root cause: Stripe's `cancel_at_period_end`
default is `true` — the subscription stays active until the end of
the current period. The activation is correctly `pro` until then.

Built a UX surface that signals this state so the user understands.

## Phase 8c — PDF outline-indent fix (PR #8)

User reported that the landscape share PDF wasn't visually indenting
child tasks despite literal whitespace being prepended. Root cause:
React-PDF's `<Text>` component collapses leading whitespace during
text shaping.

Fix in `lib/plansight-ai/pdf/share-view.tsx`:
- New `indentPtForOutline(task, baseLevel)` computes
  `(outlineLevel - baseLevel) * 8pt`.
- `normalizedBaseLevel = Math.min(...task.outlineLevel)` — some MPP
  plans start at outline 0, some at 1. Normalize so the shallowest
  task is always flush-left.
- Applied as `paddingLeft: 6 + indentPtForOutline(...)` on the task
  name `<Text>`, not as literal text.

### `lib/plansight-ai/ai-usage/`
Five modules, each best-effort (never throws on Supabase failure):
- `cost.ts` — Haiku pricing constants ($1 input / $5 output / $0.10
  cache read / $1.25 cache write per 1M tokens). `computeCostUsd`,
  `extractTokenUsage`.
- `usage-log.ts` — `logAiUsage(input)`: inserts into `ai_usage_log`.
  Defaults cost_usd to 0 for cache hits.
- `explain-task-cache.ts` — `getCachedExplanation` /
  `setCachedExplanation` keyed by content hash + task id.
- `rate-limit.ts` — `checkExplainTaskRateLimit(userId)` returns
  `{ kind: "allow" | "block", ... }`. 30/hr hard, 100/day soft,
  200/day hard. Counts non-cached, non-rate-limited rows since
  hour-ago / UTC midnight. Degrades open on Supabase outage.
- `spend-alert.ts` — `checkAndAlertSpend(userId, email)`: sums
  month's `cost_usd`, sends Resend HTTP email if > $3 and
  `ai_spend_alerts` doesn't already have a row for this month.

## Auth: magic-link → email + password (PRs #11–#13)

### Context and decisions

Goal: replace Supabase OTP / magic-link sign-in with email + password.
The product wants near-zero-friction sign-up but the email round-trip
on every sign-in was the wrong tax for a returning user. Password
sign-in is synchronous; sign-up keeps the email round-trip (Supabase
"Confirm signup" template) so we still have anti-bot + email-typo
defenses.

Implementation plan agreed up front:

- Default Supabase password sign-in (synchronous).
- Email confirmation on sign-up stays ON (one round-trip on creation,
  not on every login).
- Sign-up always lands on `/my-plans` (universal new-account dashboard
  destination), regardless of which page initiated sign-up.
- Sign-in honors the page-of-origin via `redirectTo` query param.
- New routes: `/signup`, `/forgot-password`, `/reset-password`.
- Drop magic-link entirely (no fallback). Easy to add back if users
  complain.
- Min password length: 8 (enforced client-side; Supabase dashboard
  setting is the server side of that, configured manually).
- `/auth/callback` reused for both sign-up email confirmation and
  password reset link landing (both arrive with `?code=`, both get
  exchanged via `supabase.auth.exchangeCodeForSession`, both honor
  `?redirectTo=`).

### Sub-session: data-state debugging

User emptied tables and saw a confusing state: `product_activations`
had a row but `public.users` was empty. Walked through why:

- `public.users` is populated only by the `handle_new_auth_user()`
  trigger, which fires `after insert on auth.users`. Deleting from
  `public.users` directly doesn't backfill — the auth row already
  existed.
- `activateProduct()` writes via service-role and doesn't care about
  `public.users`. It only references `auth.users.id`.
- A leftover Supabase session cookie kept the user "signed in" against
  a possibly-empty `auth.users`, surfacing the "Activate PlanSight"
  branch in the navbar (signedIn + not-activated).

Cleanest reset: `delete from auth.users;` cascades through
`public.users`, `product_activations`, `user_billing`,
`ai_usage_log`, `ai_spend_alerts`, and any `plans` with
`owner_user_id`. Then truncate guest-owned content. Provided a full
SQL reset script for the user to save:

```sql
delete from auth.users;
truncate public.plans, public.plan_tasks cascade;
truncate public.explain_task_cache;
-- verify counts return 0 across all tables
```

Also walked through how the tier model works (anonymous / free with
login / Pro) and which tables back each. Audited `public.users` table
usage: only `week_start_day` is read (by `getUserPreferences()`); the
`email` mirror, `created_at`, `updated_at` are dead weight. The orphan
state didn't cause functional bugs because the one consumer of
`public.users` defensively returns "monday" on missing row. Decision:
leave `public.users` as-is for now (small mirror, harmless), consider
a `user_preferences`-only table later.

## AI analysis cost re-architecture: bounded payload v2 (PRs #15–#18)

The big stream. Drove from
`branding/plansight-ai/AI_PAYLOAD_IMPLEMENTATION_BRIEF.md` which the
user authored separately and asked me to read. Brief argues that the
"naive" approach (full task array to Claude) breaks at ~1,500 tasks
and scales cost linearly with plan size; we need cost+latency flat
across plan sizes since Pro supports 25k tasks.

Found during the design discussion: the current code (Phase 3) wasn't
naive — `compressInsightsForPrompt()` already capped each category at
8 items. So today's payload was already ~constant size, just smaller
and missing several sections the brief specified (no milestones, no
upcoming-30, no WBS structure, no resources). The brief was effectively
asking for a richer, more documented version of what was already there.

### Architectural decisions (recorded for tomorrow's me)

1. **One path, env-flag rollback** — not a per-plan-size threshold.
   Considered a hybrid where small plans (<500 tasks) stay on v1, big
   plans use v2. Rejected: two payload shapes = two cache namespaces,
   inconsistent output across one-task boundaries, double the
   maintenance. Single architecture with `AI_PAYLOAD_VERSION=v1` as a
   one-env-var revert is cleaner.

2. **Coupling between insights and AI** — not a new problem. The AI
   already depended on insights via `compressInsightsForPrompt`. v2
   just makes the dependency more deliberate and adds more
   insights-derived sections. UI's use of insights stays separate.

3. **Where to compute the four missing sections** (milestones,
   upcoming-30, structure WBS L1-3, resources). Two options:
   - (A) Inside `buildAIPayload(plan, insights)` — keeps the insights
     engine focused on risk-bearing tasks. Smaller blast radius.
   - (B) Extend `buildInsightsReport()` so insights becomes the
     single source of truth for "what's worth attention." Heavier
     refactor.
   User chose (A); B is a follow-up if a future UI feature wants the
   same data.

### Phase 0 — Audit + hotfixes (PR #15, merged as `3ee3a5f`)

Before piling more weight on the insights engine, full audit of
`lib/plansight-ai/analysis.ts` (~932 lines). Found three real perf hot
paths and one almost-certain bug; surgical fixes shipped before the
payload work:

- **P1a — `Array.shift()` in `topologicalOrder()`**. Shift is O(N)
  because JS arrays reindex. Kahn's algorithm at 25k tasks burns ~625M
  ops in the queue alone. Replaced with `let head = 0; const id =
  queue[head++]`. Restores O(V + E).
- **P1b — nested `.some()` for ID lookups in `buildInsightsReport()`**.
  `criticalLateCount` and `criticalAtRiskCount` ran `O(critical × late)`
  and `O(critical × atRisk)`. Pre-built `Set<number>` of IDs once,
  lookups now O(critical).
- **C1 — tautological ternary on line 825**:
  `approximateMode ? critical.criticalTasks : critical.criticalTasks`.
  Both branches identical. In approximate mode `critical.criticalTasks`
  is empty by design (CPM has no zero-slack path with no deps; data
  goes into `potentialCriticalTasks` instead). Cleanup makes that
  explicit with a comment; behavior unchanged. The bug we fixed is
  now: any consumer that wants critical tasks in approximate mode
  needs to read `potentialCriticalTasks`. `buildAIPayload` handles
  this explicitly.
- **C2 — `MY_TASK_OWNER = "Angelito Crisologo"` constant**. Hardcoded
  the user's name to drive a `myTasks` counter in `PlanMetrics`. Only
  consumer was `PlanSightAnalysisPanel.tsx`, never imported anywhere.
  Removed: the constant, the increment block, the `PlanMetrics.myTasks`
  field, and the orphan component file (~307 lines deleted). Hardcoded
  owner name was a privacy footgun for a multi-tenant SaaS.

**Deferred to Phase 1 PR (P2)**: `buildCriticalPaths()` recursive DFS
is exponential under pathological inputs (parallel zero-slack chains
converging). Folded into the payload-builder PR as a bounded `MAX_CRITICAL_PATHS = 50` guard.

User confirmed measured improvement after deploy: "share page loads
faster" — matches the algorithmic estimate (25k-task case dropped from
~5-10s of pure insights work to ~300-500ms).

### Phase 1+2+3 — Payload module + Vitest + 22 tests (PR #16, merged as `92963b6`)

Single PR because the three phases are pointless individually. Six new
files in `lib/plansight-ai/ai-payload/`:

- **`types.ts`** — `AIPayload` contract, `PAYLOAD_CAPS`, sections:
  meta, health, criticalTasks (≤20), lateTasks (≤20), atRiskTasks
  (≤20), milestones (≤15), bottlenecks (≤10), upcoming (≤30, next 30
  days), structure (≤50, WBS L1–3 summary nodes), resources (≤10,
  with `overallocated` flag), referencedTaskIds.
- **`build-ai-payload.ts`** — pure function
  `buildAIPayload(plan, insights, opts)`. Computes
  milestones/upcoming/structure/resources locally from the plan; uses
  the insights engine for the risk-bearing sections. Approximate-mode
  fallback: when `insights.mode === "approximate"` the `criticalTasks`
  section sources from `insights.potentialCriticalTasks` instead.
  Per-task entries carry: id, name, start/finish, durationDays,
  percentComplete, flags `{critical, late, atRisk, milestone,
  bottleneck}`, predecessorIds (capped at 5, deduped, in declaration
  order). `referencedTaskIds`: every distinct predecessor ID across
  all included tasks — lets Claude name IDs even when the predecessor
  task isn't in the included sections.
- **`token-estimate.ts`** — `estimatePayloadTokens(payload)` using
  Anthropic's 4-chars-per-token heuristic on compact JSON.
- **`__tests__/fixtures.ts`** — deterministic seeded LCG-PRNG plan
  generator. Produces L1/L2/L3 WBS hierarchy, linear FS dependency
  chains within each phase, 12-name resource pool, milestones every
  ~25 leaves, progress derived from date-vs-today.
- **`__tests__/build-ai-payload.test.ts`** — 22 tests covering token
  budget (3k-10k for 100/1.5k/10k), cap respect on a large plan,
  caps actually hit (structure/resources/bottlenecks/critical/late/
  atRisk), `predecessorIds` per-task cap, milestone flagging, section
  sort orders, upcoming window date filter, `referencedTaskIds`
  completeness + ascending order + no dupes, meta/health correctness,
  approximate-mode fallback, no raw-plan leak.

Vitest setup: new `vitest.config.ts` mirroring tsconfig's `@/*` alias,
new `test` and `test:watch` scripts in `package.json`. `vitest` as a
dev dep only — explicitly **not** added to `next build`, so Vercel
deploys don't run tests (kept out of the build pipeline on purpose).

Brief mentioned a doc spec deliverable; deferred that to PR #18.

Measured token counts from the fixture suite:
- 100 tasks → ~1.2k tokens
- 1,500 tasks → ~3.5k tokens
- 10,000 tasks → ~4.5k tokens

Plenty of headroom to widen caps later if Claude wants more context.

Pre-existing security findings from `npm audit` (5: 1 mod, 4 high) all
trace to Next.js 14.x line and its transitive deps. Not introduced by

### Phase 4 — Wire v2 into ai.ts (PR #17, merged as `1f9c1dc`)

The PR that actually changes what Claude sees. `generateAiAnalysis()`
now dispatches on `AI_PAYLOAD_VERSION`:

- unset / `"v2"` / anything else → v2 (default).
- `"v1"` → legacy `compressInsightsForPrompt` path, untouched. Kept
  as a one-env-var emergency rollback.

`resolvePayloadVersion()` reads per-request, so flipping the var in
Vercel takes effect on the next call — no redeploy. Each generation
logs `[ai-analysis] payload version: vN` so `ai_usage_log` rows can be
correlated to the version that produced them.

**Layered prompt caching**: `callClaude()` gained an optional
`cachedSchemaHeader` parameter. v2 puts the `PAYLOAD_SCHEMA_HEADER`
(describing the AIPayload shape) into a second cached system block
alongside the existing system prompt. Anthropic's ephemeral cache
discount applies to system prompt + tool definitions + schema header
(the stable surface); only the user-message body (the actual payload
JSON) varies. v1's single-block caching is unchanged.

Both v2 Claude calls (findings + recommendations) now receive the
**same** bounded payload — previously the recommendations call only
got the findings + compressed insights. Per the brief §3: "Both calls
use the same bounded payload contract."

v2 prompts (`FINDINGS_SYSTEM_PROMPT_V2`, `RECOMMENDATIONS_SYSTEM_PROMPT_V2`)
are close to v1 wording but reference new payload section names and
tell Claude it can reference task IDs in `referencedTaskIds` even when
the task itself isn't in the included sections.

Dev-mode token guard: `console.warn` fires if a real payload exceeds
9k tokens, so we'd notice if a real plan's data is pushing close to
the 10k ceiling. Production is silent; the test suite + per-section
caps are the real safety net.
