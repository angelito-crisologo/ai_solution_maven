## Phase 10 — Upload telemetry (PR #20)

Implementation brief at `docs/plansight-ai/archive/UPLOAD_TELEMETRY_IMPLEMENTATION_BRIEF.md`
spec'd a single `upload_events` table covering every `.mpp` upload
attempt — success or failure — with parser-pipeline timings and a
small failure-stage taxonomy.

### Decisions on scope

User confirmed v1 scope:

1. Instrument **only** `/api/plansight/import-mpp` (not `/share`).
2. Filename hashing (SHA-256) instead of storing filenames.
3. No privacy policy yet (deferred).
4. Admin dashboard deferred to phase 11.

### Code shipped

- `supabase/migrations/10_phase10_upload_events.sql` — `upload_events`
  table with three indexes (`created_at`, `(success, created_at)`,
  partial `(failure_stage) WHERE success=false`). RLS deny-all; only
  service-role writes.
- `lib/telemetry/upload-events.ts`:
  - `recordUploadEvent(event)` — fire-and-forget insert, never throws.
  - `classifyError(err)` — maps caught errors to a `FailureStage`
    (`parser_timeout`, `parser_error`, `db_write`, `unknown`).
  - `sanitizeError(msg)` — redacts headers and stack-trace shapes
    from failure messages; ≤300 chars.
  - `hashFilename(name)` — SHA-256 via Web Crypto.
- `lib/telemetry/__tests__/upload-events.test.ts` — 25 unit tests
  covering classification, sanitization, hashing, fire-and-forget
  semantics.
- `app/api/plansight/import-mpp/route.ts` — instrumented via a local
  `respond()` helper at every return site. Each success and failure
  records timing, tier, sanitized error, etc.
- Spec at `docs/plansight-ai/specs/telemetry.md` (moved here in PR #27).

### Bug fixed mid-PR

Header-redaction regex used `[^,\s]+` which stops at whitespace,
leaving `Basic dXNlcjpwYXNz` exposed after the keyword. Fixed by
changing to `[^,;]+` so the redactor consumes through the next
separator. Test in `__tests__` covers it.

### Fix admin RSC boundary (PR #25)

After the move, production hit a 500 on the new admin route. Vercel
logs surfaced two RSC bundler errors:

1. `Could not find the module ".../AdminCharts.tsx#ADMIN_CHART_COLORS#primary" in the React Client Manifest`
   — exporting a plain object from a `"use client"` module and
   accessing `.primary`/`.danger` from a server component breaks
   the manifest. Properties can't be resolved through the client
   reference proxy.
2. `Functions cannot be passed directly to Client Components unless you explicitly expose it by marking it with "use server"`
   — the page was passing `yFormatter={(v) => ...}` to a client
   chart component. Server→client function props are forbidden.

Fix:

- Extracted `ADMIN_CHART_COLORS` and a `ChartValueFormat` union into
  a non-client module: `app/products/plansight-ai/admin/chart-constants.ts`.
  Server page and client charts both import from this.
- Replaced function `yFormatter`/`xFormatter` props with a
  `valueFormat: "usd" | "ms" | "bytes" | "int"` discriminator. The
  client chart resolves the formatter internally.

After deploy, `/products/plansight-ai/admin` rendered 200 with all
four sections.

## Product #2 prep (PR #29) + migration 12

User asked whether the codebase is fully isolated between products
so a second product could slot in without rework, while still
leveraging shared infrastructure (auth across products). Audit
found the bones were right (slug-based routing, per-product
activation, per-product branding) but several leaks remained.

### Six items shipped

1. **Slug consolidation** — new `lib/products.ts` is the single
   source of truth for `PRODUCT_SLUGS`. `PRODUCTS` (in
   `lib/auth/activations.ts`) and `BRANDS` (in `lib/branding/index.ts`)
   derive from it. Adding product #2 = one line in `PRODUCT_SLUGS`.
   Typo at any callsite becomes a TS error.

2. **Shared Supabase service client** — `lib/plansight-ai/supabase.ts`
   → `lib/supabase/service.ts`. 12 import sites updated. Pure rename;
   removes the awkward "shared helpers import from a product folder"
   cross-dependency.

3. **Neutralized auth redirects** — `/signin`, `/forgot-password`,
   `/reset-password`, and `/auth/callback` defaults changed from
   `/products/plansight-ai/my-plans` to `/`. Sign-up still
   product-aware via `?product=<slug>` when present. Removes the
   PlanSight bias from the parent auth flows.

4. **Fixed `SignInForm` signupHref** — was hardcoded to
   `?product=plansight-ai&redirectTo=%2Fmy-plans` (also a stale path
   after PR #26). Now carries the caller's destination forward
   without baking in a product slug — the page only renders for
   no-product flows anyway.

5. **`/upgrade` moved under the product** — `app/upgrade/page.tsx`
   → `app/products/plansight-ai/upgrade/page.tsx`. All PlanSight
   internal links updated; Stripe `cancel_url` updated; `/upgrade`
   kept as a tiny redirect stub so in-flight Stripe sessions and
   external bookmarks still resolve.

6. **`product_slug` on telemetry tables** — migration 12 adds
   `product_slug TEXT NOT NULL DEFAULT 'plansight-ai'` to
   `upload_events`, `ai_usage_log`, and `share_views`, plus a
   `(product_slug, created_at_or_viewed_at DESC)` index on each.
   The default backfills existing rows transparently. Telemetry
   writers updated to pass the slug. Without this, a second product
   would either share opaque telemetry rows with PlanSight or need
   parallel tables.

### Migration 12 bug fix

First migration run failed:


`share_views` uses `viewed_at`, not `created_at` (per migration 11).
The third index referenced the wrong column. Fixed and re-ran;

## Restore retry-on-empty for AI recommendations (PR #30)

User reported the "AI didn't return specific recommendations. Try
regenerating." message was back. Pulled Vercel logs and confirmed:

```
[ai-analysis] submit_recommendations input keys: []
[ai-analysis] recommendations call returned 0 items; preview: {}
```

Claude was invoking the forced `submit_recommendations` tool with an
empty `{}` input — bypassing the schema's `minItems: 1`. Forced
`tool_choice` doesn't enforce inner constraints.

User asked "did we revert non-working code?" — git log confirmed
yes:

- Commit `5876aaf` ("Phase 3: few-shot prompt + retry-on-empty for
  recommendations") added a corrective `tool_result` turn that
  replayed the model's empty output back as context and asked
  specifically for the missing field.
- Commit `da21fde` ("Phase 4: wire bounded AI payload v2 into ai.ts")
  preserved the two-call findings/recommendations split but **dropped
  the retry safety net**.

So the model could still send `{}` and there was nothing catching it
anymore.

### Fix

Added `retryRecommendationsIfEmpty()` helper. When the first call
returns 0 recommendations, it:

1. Captures the empty `tool_use` block from the response
2. Replays it as an assistant turn
3. Sends a corrective `tool_result` user turn flagging the failure
   and listing valid imperative verbs (Reassign, Reschedule, Confirm,
   Update, Convene, Review, Escalate, Reduce, Re-baseline, Delegate,
   Validate)
4. Calls Claude once more with the same tool

Applied to both v1 and v2 paths so the `AI_PAYLOAD_VERSION` env-var
rollback lever still works end-to-end. If retry also returns empty,
the route logs and returns `[]` — same fallback behavior, just one
more chance.

Cost: +1 Haiku call only when the first attempt is empty. Content-hash
cache absorbs this — each plan pays the cost once.
