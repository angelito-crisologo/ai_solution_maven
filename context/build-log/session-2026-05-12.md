## Restore retry-on-empty for AI recommendations (PR #30)

User reported the "AI didn't return specific recommendations. Try
regenerating." message was back. Pulled Vercel logs and confirmed:

```
[ai-analysis] submit_recommendations input keys: []
[ai-analysis] recommendations call returned 0 items; preview: {}
```

Claude was invoking the forced `submit_recommendations` tool with an
empty `{}` input — bypassing the schema's `minItems: 1`. Forced
`tool_choice` doesn't enforce inner constraints.

User asked "did we revert non-working code?" — git log confirmed
yes:

- Commit `5876aaf` ("Phase 3: few-shot prompt + retry-on-empty for
  recommendations") added a corrective `tool_result` turn that
  replayed the model's empty output back as context and asked
  specifically for the missing field.
- Commit `da21fde` ("Phase 4: wire bounded AI payload v2 into ai.ts")
  preserved the two-call findings/recommendations split but **dropped
  the retry safety net**.

So the model could still send `{}` and there was nothing catching it
anymore.

### Fix

Added `retryRecommendationsIfEmpty()` helper. When the first call
returns 0 recommendations, it:

1. Captures the empty `tool_use` block from the response
2. Replays it as an assistant turn
3. Sends a corrective `tool_result` user turn flagging the failure
   and listing valid imperative verbs (Reassign, Reschedule, Confirm,
   Update, Convene, Review, Escalate, Reduce, Re-baseline, Delegate,
   Validate)
4. Calls Claude once more with the same tool

Applied to both v1 and v2 paths so the `AI_PAYLOAD_VERSION` env-var
rollback lever still works end-to-end. If retry also returns empty,
the route logs and returns `[]` — same fallback behavior, just one
more chance.

Cost: +1 Haiku call only when the first attempt is empty. Content-hash
cache absorbs this — each plan pays the cost once.

## Anonymous TTL to 24 hours + claim-on-signup mechanic (31e1f6b, c32f078, dfa162b, ac7dd9a)

The pricing section now advertised "Plan kept 24 hours" for the Anonymous tier, but the backend's actual TTL was 30 days. Worse, the planned conversion pitch — "sign up to keep this plan" — was unbacked: signing up after an anonymous upload didn't actually transfer ownership. The claim flow had to be built before the banner promise was honest.

### Code TTL change (31e1f6b)

`lib/plansight-ai/guest.ts` exported `getGuestPlanExpiryIso(days = 30)`. The call site at `lib/plansight-ai/share-storage.ts:320` passed `30` explicitly. Both updated: the function now takes `hours = 24` and the call site passes `24`. The comment was rewritten to say so explicitly.

An in-product banner accompanies the change: when an anonymous visitor has a plan loaded, the workspace shows a persistent cyan-200-bordered panel headlined "This plan expires in 24 hours" with a `Save my plan — sign up free` CTA. The banner replaced an existing, weaker "Want this plan still here next time?" surface.

### Claim mechanic (c32f078)

A subagent verified the funnel had a broken promise: signup didn't claim the anonymous plan. Built the missing flow as four pieces:

1. **Banner click handler** writes `plansight:claim-share-id` to localStorage before navigation. Honours modifier-click (cmd/ctrl/shift/middle) so "open in new tab" still works.
2. **`/api/plansight/claim` POST route** (new file) accepts `{ shareId }`, requires a session, calls `claimGuestPlan(shareId, userId)`, returns 200 / 404 / 410 / 500. Best-effort activates PlanSight after a successful claim.
3. **`claimGuestPlan(shareId, userId)`** in `lib/plansight-ai/share-storage.ts`: validates the row is `owner_type='guest'` and not expired, then UPDATEs `owner_type='user'`, `owner_user_id=session.user.id`, `expires_at=NULL`. Returns a discriminated result for not-found / not-guest / expired.
4. **Workspace useEffect** fires on `signedIn` mount: reads localStorage, POSTs to the claim route, clears localStorage immediately so transient errors don't loop. On success, reloads via `?shareId=…` so the server-rendered shell hydrates with the now-owned plan.

### Authorisation trade-off

Any signed-in user can claim a guest row by `shareId`. A stakeholder who received an anonymous share URL could in principle race the uploader to ownership. Accepted for v1 — anonymous rows expire in 24h anyway, and the uploader can sign up first. If this becomes a real concern, the fix is a guest-session HttpOnly cookie scoped to the shareId at upload time. Documented in the `claimGuestPlan` JSDoc.

### Land signups on `/my-plans` (dfa162b)

After shipping the claim flow, the user asked for the post-signup landing to be `/my-plans` rather than the workspace. Three changes:

## Critical-path duration single source of truth (15394f6)

User reported that `Home Move` showed four critical paths with durations 50, 50, 50, 51 — and asked whether multiple critical paths were correct CPM behaviour, why three of the four were off by a day, and why an earlier observation had shown 80/81.

### What the algorithm actually does

`lib/plansight-ai/analysis.ts:computeCriticalPath` runs textbook CPM: forward pass for Earliest Start / Earliest Finish, backward pass for Latest Start / Latest Finish, slack = LS − ES, critical tasks are zero-slack, `buildCriticalPaths` DFS-enumerates every chain through critical tasks. Path duration = sum of `task.durationDays` along the chain. The function filters to only paths whose sum equals `maxDurationDays`. So the *engine* believed all four paths were tied at the same length — multiple critical paths is a real, common pattern in plans with parallel chains that converge.

### Why the UI showed different durations

`components/plansight-ai/PlanSightProjectInsightsPanel.tsx` was re-deriving each path's duration independently from the engine, summing `(finish - start + 1)` per task via `Math.round(diffMs / 86400000) + 1`. The engine used `toDayIndex` (UTC midnight-normalised day indices, `Math.max(1, ...)`-floored). On plans with a task that straddled a DST boundary, the millisecond rounding produced off-by-ones; one DST-affected task per path was enough to make the UI label otherwise-equal critical paths as 50 instead of 51.

### Fix

Promoted the path entry shape from `string[]` to `{ taskIds: string[]; durationDays: number }`. The analysis layer emits the duration it already has; the UI just reads it. `lib/plansight-ai/ai-payload/build-ai-payload.ts:computeCriticalPathDuration` became a one-line lookup of `criticalPaths[0].durationDays`. The UI's `criticalPathCards` memo no longer touches dates; the now-unused `criticalTaskById` map was deleted.

### Why 80 → 50 — separate issue

A subagent queried prod Supabase to inspect the `Home Move` row. Project window: Aug 3 – Sep 30 2020 (59 calendar days). 126 schedulable tasks. The current critical path of 51 days fits naturally. The earlier 80/81 the user remembered must have been against a different version of the .mpp — re-uploading the file generates a fresh `share_id` and the previous data is gone. Not a code regression; data drift between observations.

### Files touched

- `lib/plansight-ai/analysis.ts` — type change, emit `durationDays`, four empty-array initialisers updated
- `lib/plansight-ai/ai-payload/build-ai-payload.ts` — simplified to a direct lookup
- `components/plansight-ai/PlanSightProjectInsightsPanel.tsx` — dropped UI recompute and unused memo

### File-tracing bug surfaced and fixed (ae0edfb, 506db0d)

First attempt at the route worked locally but rendered the "PlanSight AI guide" fallback title in prod across all three guides. Root cause: Next's file-tracer can't statically detect `fs.readFile` calls against a runtime-computed path, so the `content/plansight-guides/` directory was pruned from the deploy artefact. The slug page itself wasn't affected because it reads at *build* time during `generateStaticParams` + `generateMetadata`; the OG image route reads at *request* time on Vercel with only bundled files available.

Fix: `outputFileTracingIncludes` in `next.config.mjs` explicitly tells Next to bundle `content/plansight-guides/**` with any function under `/products/plansight-ai/guides/**`.

`ae0edfb` placed the option at the top level of the config, which is correct for Next 15 but silently no-ops on Next 14.2.x. The route subsequently 404'd in prod (likely because the unknown option triggered some build-time validation that pruned the route). `506db0d` moved the option under `experimental` where Next 14 honours it, and the route + per-guide titles came back live. Documented in the commit message so the next contributor knows the option's location depends on Next version.
