## The Phase 15 share-gate bug

Symptom at start of session: revoking a share via the new Manage
Share dialog set `share_revoked_at` correctly in the DB (verified in
the Supabase SQL editor), but opening the share link in incognito
still rendered the plan. Restoring had the mirror problem — DB
cleared, page still showed "no longer available."

### Diagnosis path

Walked through layers in this order:

1. **PostgREST schema cache.** First hypothesis: the Phase 15
   columns (`share_revoked_at`, `share_password_*`) weren't visible
   to the anon role via PostgREST even after `notify pgrst, 'reload
   schema'`. Switched `getShareSecurityStatus` to the service-role
   client. The `[share-gate]` log showed `revoked: true` for already-
   revoked rows after this, suggesting the read fix worked.
2. **But restore still failed.** New plan, revoked, then "restored"
   — the gate still reported `revoked: true, passwordVersion: 1`. If
   restore had actually run the UPDATE the version would be 2. So
   either the route wasn't called, or it bailed before the write.
3. **Added entry-level logging on the restore route.** Next test:
   `[share-restore:write]` fired correctly, returning `{ share_revoked_at:
   null, share_password_version: 2 }`. Write was good.
4. **The smoking gun.** A separate test: revoke at 09:21:59 returns
   `{ share_revoked_at: <timestamp>, version: 10 }` from the UPDATE.
   The share-gate read at 09:22:47 — 48 seconds later — returned
   `{ raw_share_revoked_at: <09:18:00 timestamp>, raw_password_version:
   9 }`. The values from *before* the revoke. The DB was right; the
   response was being served from cache.

### The fix

`dynamic = "force-dynamic"` on the share page opts out of the full-
route cache but does not propagate `cache: "no-store"` to fetches
made inside imported helpers. supabase-js issues a plain GET that
the Next.js fetch wrapper happily memoises in the Data Cache.
Overriding the service client's `global.fetch` to set `cache:
"no-store"` forces every read through to Postgres:

```ts
// lib/supabase/service.ts
return createClient(config.url, config.serviceKey, {
  auth: { autoRefreshToken: false, persistSession: false },
  global: {
    fetch: (input, init) => fetch(input, { ...init, cache: "no-store" })
  }
});
```

Verified end-to-end after deploy: revoke, restore, password set,
password clear, password verify all work correctly across multiple
back-to-back cycles.

### Memory written

Saved as `feedback_supabase_data_cache.md` in auto-memory so the
next authenticated read doesn't repeat the same 6-commit debug
cycle: **supabase-js reads via service role need `cache: "no-store"`
even on `force-dynamic` routes.**

### Debug logs removed

`afde125` strips the four temporary `[share-gate]`, `[share-gate:read]`,
`[share-revoke:write]`, `[share-restore:*]` traces now that the bug is
fixed.

### Surfaces (`d1c3a6b`)

HTML GET form — shareable, bookmarkable, JS-optional. CSV download
button on each page calls `GET /api/admin/feedback/export` with the
same query params, returning RFC-4180-ish CSV with a UTF-8 BOM so
Excel reads it cleanly. Capped at 1000 rows, filename
`feedback-<slug>-YYYY-MM-DD.csv`. Same admin gate as the pages.

## Two production bugs caught after launch-improvement deploys

### GFM tables weren't rendering (`069d413`)

User reported the comparison table in the new PDF guide rendered as
raw pipe-separated text. Root cause: `next-mdx-remote` v6 ships
CommonMark only; GFM (tables, strikethrough, task lists, autolinks)
requires `remark-gfm` which was never installed. The legal docs
(`privacy.md` sub-processors and retention tables) had the same
latent bug — table components defined in the renderer but the
parsing plugin missing.

Fix:
- Add `remark-gfm` to dependencies.
- Pass `mdxOptions: { remarkPlugins: [remarkGfm] }` to both
  MDXRemote instances (guides + legal).
- Add `table` / `thead` / `th` / `td` components to the guide
  page's `mdxComponents`, matching the legal page's existing
  table styling.

### Broken monogram path on the stakeholder page (`3f52d45`)

The stakeholder-page attribution card referenced
`plansight-monogram.svg`, but the brand assets are all suffixed
(`-dark`, `-light`, `-simplified`). Switched to the `-light`
variant since the card sits on a slate-50 surface.
